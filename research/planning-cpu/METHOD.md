# 長期計画CPUの検証条件

2026-10-08。ゲーム内への反映を決める前に、研究用CPUだけを比較する。

## CPUの変更

既存の研究用CPUは、8つの固定方針が提案する行動を、現在～次ラウンドの仮想ゲームで比較する。高額カードの保持判断は主に現在のお金＋3金までを見ている。

新CPUは、次の両方を比較する。

- 8方針の提案を現在から最大4ラウンド処理する。
- 現在の手札だけで最大4ラウンドの合法な配置順を探す。得点・揃えを重視する候補と、前線を保つ候補を作る。必要なカードを使う時期まで保持する案を追加する。

計画候補の生成では、相手が追加配置しない近似で手札内の完成筋を絞る。候補の最終比較では、公開情報から生成した2通りの仮手札・山札で、相手も配置・交換し、実際の終了条件まで処理する。計画が未完了でも相手が9体または40VPへ到達すれば終了する。候補の評価は平均85%＋最悪ケース15%。次の実際の手札では計画を選び直す。君主ルートのカード名や手順をCPUへ特別登録していない。

同じ予測条件で比較するが、行動が違えば補充枚数も変わるため、以後に引くすべてのカードが同じとは限らない。相手の実際の手札・山札順・同時提出する行動は使わない。検討中に実際のゲームを変更しない。

## 比較群

各群は同じ乱数種・初手・自分の位置から、自分だけを変更する対照比較。全員の注文を提出前の盤面から先に決める。

| 群 | 対照 | 相手 | 配札条件数（本比較／独立追加） |
|---|---|---|---|
| natural | 既存研究CPU／新CPU | 均衡評価型 | 各2～5人で32／32 |
| production | ゲーム内の凄腕／新CPU | 凄腕 | 各2・5人で16／16 |
| royal | 既存研究CPU／新CPU | 均衡評価型 | 各2・5人で16／16、理想初手を設定 |
| lookahead | 計画候補なしの4ラウンドCPU／新CPU | 均衡評価型 | 各2・5人で16／16 |

本比較448対戦、別の乱数種による追加448対戦。理想君主手札は自然な配札と混ぜない。初手出現率はこの実験では測らない。対戦の引き分けは勝利を分配して集計する。

lookahead群は、仮想世界の数・先読み期間・固定方針・配置探索幅を合わせて計画候補だけを外した対照。新CPUには計画生成ぶんの追加計算があるため、計算量そのものまで等しい比較ではない。

## 反映の判断

各人数の勝利シェア、同じ条件での差、同じ乱数種を人数違いも含めてまとめた再標本化による95%区間、VP差、君主ボーナス完成率、判断時間を記録する。本比較と追加検証を別に示し、同じ最終コードの結果のみを統合する。

ゲーム内への反映は次を確認してから判断する。

1. 全対戦が合法に完走し、102枚のカードを保存する。初期配札の一致と、保存結果の再現を確認する。
2. natural群全体で勝利シェア差の95%区間が正になる。追加検証でも平均差が正で、特定人数の大きな悪化がない。
3. production群でも全体の平均差が正で、95%区間が明確な悪化を示さない。対照は凄腕なので、確認できても全難易度の改善とは呼ばない。
4. 単独実行で判断時間を測り直す。5人戦で1判断が継続的に1秒を超える場合は、そのままゲーム内に入れない。並列実験中の時間をブラウザの応答時間として扱わない。

条件を満たさなければ研究用コードと結果を保存し、ゲーム内CPUは変更しない。単に理想君主ルートが改善しただけでは反映しない。

## 再実行

Node.js 22以上、リポジトリ直下：

```sh
node scripts/benchmark-planning.mjs
node scripts/benchmark-planning.mjs --validation
node scripts/analyze-planning.mjs results --replay
node scripts/analyze-planning.mjs validation --replay
```

PLANNING_SEEDSでnatural群の条件数、PLANNING_WORKERSでワーカー数を変更できる。他群は条件数の半分、最低8条件。コードや条件が変わった場合は過去の設定・データを別フォルダへ保管する。予備実行は設計・記録処理の確認だけに使い、最終数値へ混ぜない。実測時間だけは再現照合の対象から外す。
